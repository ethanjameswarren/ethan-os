# Schedule Adaptation

## What it does

Turn repeated schedule overrides into structured behavioral evidence, detect when the baseline schedule no longer matches real life, and propose corrections with human approval.

## Why it exists

Most schedules drift over time. Plans that once worked stop working as routines, constraints, and preferences change. Ethan OS records every override as evidence and uses simple statistics to decide whether the plan itself should change.

## Core loop

```
baseline schedule
 → schedule used in real life
 → override occurs
 → capture structured evidence
 → accumulate history
 → detect repeated patterns
 → determine whether pattern is meaningful
 → propose baseline correction
 → user accepts/rejects
 → validate new baseline over time
```

## What you do

- Describe a schedule change in plain language, e.g. "Move Learning tonight from 7 to 8:30 because I got home late."
- Accept or reject baseline correction proposals.
- Optionally ask for a schedule-drift analysis.

## What Ethan OS does

- Captures every override with structured fields: original block, actual block, change effect, classification, and reason.
- Classifies overrides as `exception`, `preference`, `friction`, or `unknown`.
- Analyzes override history for each recurring block.
- Detects emerging patterns and schedule drift against configurable thresholds.
- Generates evidence-backed baseline correction recommendations.
- Applies baseline changes only after explicit user approval.
- Tracks post-change behavior to validate whether the correction worked.
- Feeds meaningful patterns into weekly planning and review without noise.

## Key ideas

### Repeated deviation is information

Ethan OS does not assume the user failed to follow the schedule. It evaluates whether the schedule failed to model the user's real behavior.

### Exceptions do not rewrite routines

A concert, illness, or trip is an exception. One-off exceptions are recorded but do not influence the baseline.

### Preference and friction look different

A preference is a consistent voluntary change. Friction is evidence that the plan is systematically unrealistic or conflicted.

### Approval before mutation

The canonical baseline schedule is never rewritten without explicit user approval. The system can detect, analyze, and recommend, but the user decides.

### Validation is longitudinal

An accepted change is followed for several occurrences. If overrides decrease, the correction is validated. If not, learning continues.

## What gets saved

- **Raw overrides** — unchanged historical records (`ethan-life/domains/planning/schedule-overrides/`).
- **Drift reports** — generated by `workflows/planning/analyze-schedule-overrides.md`.
- **Recommendation records** — accepted or rejected correction proposals.
- **Validation reports** — before/after override rates for accepted changes.

## Reusable pattern

Schedule adaptation is the first domain using the PLAN → OBSERVE → CAPTURE DEVIATION → ACCUMULATE EVIDENCE → DETECT PATTERN → RECOMMEND CORRECTION → APPROVE → APPLY → VALIDATE loop. The same loop can later apply to budgets, workouts, reading plans, and task estimates.
